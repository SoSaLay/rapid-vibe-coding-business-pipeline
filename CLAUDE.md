# Rapid Vibe Coding Business Pipeline

A personal, localhost orchestrator that takes an idea from raw thought → spec → validated market → (eventually) built, deployed, and marketed product. Each business phase is a self-contained module connected only through shared **artifacts**, so phases and tools are plug-and-play.

> **For the AI agent reading this:** This file is the durable, in-repo source of truth for how this project is built (architecture + conventions). **Progress and the task checklist live in `WORK-TO-BE-DONE.md`** — read it at the start of each session to see what's done and what's next, and check off `[x]` items / add tasks as you complete work. There is also a richer running log in the user's Claude memory (`~/.claude/projects/<this-project>/memory/MEMORY.md`). The user builds this **one phase at a time** and supplies the tools to integrate per phase; don't scaffold ahead. Keep everything behind interfaces so tools stay swappable.

## Run it

```bash
pnpm install
pnpm dev        # http://localhost:3000  (phone: http://<LAN-IP>:3000)
npx tsc --noEmit   # typecheck (run after changes)
```

Node 22, Next.js 14 (App Router), React 18, TypeScript, Tailwind v3. Local file storage (no DB). Keys/secrets are pasted in-app and stored under `data/` (gitignored) — never hard-coded.

## Architecture

### The spine (shared by every phase)
- `lib/pipeline.ts` — the canonical phase list (`PHASES`), each with `consumes`/`produces` artifact types and a `gate` (`required` | `optional`). **Single source of truth for ordering + the status/gating layer.**
- `lib/store.ts` — the **artifact envelope** + project store. Artifacts are versioned JSON on disk:
  - `data/projects/<id>/meta.json` — `ProjectMeta` (title, `current_phase`, `phase_status` map: locked|available|active|complete|skipped|rejected)
  - `data/projects/<id>/artifacts/<type>.v<n>.json` — the envelopes
  - `data/projects/<id>/phase-state/<phaseId>.json` — a phase's mutable working scratchpad
  - Helpers: `createProject`, `saveArtifact`, `listArtifacts`, `latestArtifact`, `get/savePhaseState`, `completePhase`, `skipPhase` (optional phases only).

**The artifact envelope is the only cross-phase contract.** A phase reads the artifacts it depends on and writes a new one. That's what makes it plug-and-play.

### Pluggable services (same registry pattern each time)
- `lib/connectors/` — project-management intake (Notion fully wired; ClickUp/Jira/etc. are identical-shape `coming_soon` stubs). Interface in `types.ts`, registry in `registry.ts`, credentials in `config.ts`.
- `lib/llm/` — the AI engine behind phases. `LlmProvider` interface; Claude (`anthropic.ts`, model `claude-opus-4-8`, adaptive thinking, structured outputs `output_config.format`, prompt caching) is the active provider via `activeProvider()`.
- `lib/frameworks/` — the **framework-pack layer**. Loads pm-skills playbooks vendored under `vendor/pm-skills/` (MIT, see `ATTRIBUTION.md`) and exposes them so phases can inject proven PM frameworks into the LLM's context. Phase-agnostic and reused across phases.
- `lib/exa.ts` — Exa search client (online signal for the Market Researcher phase). Key pasted in-app. **Note: Exa cannot search Reddit** (Reddit blocked crawlers in 2024) — `reddit.com` is excluded; forums-in-general work well.
- `lib/google/genai.ts` — Google AI (Gemini) client. Key pasted in-app (`data/connectors/google-ai.json` or `GOOGLE_AI_API_KEY`/`GEMINI_API_KEY`). REST via fetch, no SDK. The one Google key powers Stitch-mode design today and is the planned surface for Nano Banana (images) + Veo (video). **Note: Google Stitch has no public API** — it's web-only; we replicate it via the Gemini API.
- `lib/design/engine.ts` — the **design-engine layer** for Product Design Stage 2 (screen mockups). `DesignEngine` interface with two impls: `claude-html` (always available) and `google-stitch` (Gemini-backed Stitch-mode). `activeDesignEngine(projectId)` honors the project's stored choice (`settings.designEngine` — the pipeline-wide model selector), else prefers Stitch when Google is connected, else Claude. Both share one HTML contract so storage/preview/UI are engine-agnostic.
- `lib/brand-assets.ts` — the **brand-asset layer**: Nano Banana images (logo/hero/OG/campaign) + Veo videos, stored per-project under `data/projects/<id>/assets/` with an `index.json` manifest. Prompt builders follow Google's Nano Banana guidance (narrative, positive framing, quoted in-image text) and derive prompts from artifacts — no manual entry. Assets flow FORWARD: Pre-Marketing seeds → Product Design locks into the design-spec → Marketing builds campaign media on the locked brand. Also holds the Pomelli handoff builder (Pomelli is web-only — no API).
- `lib/brand-direction.ts` — the **creative-direction** step: proposes 3 distinct text directions BEFORE any pixels; the founder's pick (`settings.brandDirection`, via `lib/store.ts` project settings) seeds every image + UI prompt across phases.
- **Animation:** generated UIs are alive, not static. Landing pages (deterministic renderer) get a curated CSS motion layer (aurora, scroll-reveal, hover lifts) + an opt-in Three.js/WebGL shader hero; Product Design mockups instruct both engines to add purposeful motion. Everything is `prefers-reduced-motion`-aware.

### Per-phase pattern (how to add the next phase)
1. Add/confirm the phase in `lib/pipeline.ts` (`consumes`/`produces`/`gate`).
2. Logic in `lib/phases/<phase>.ts` — reads upstream artifact(s) via `latestArtifact`, calls `activeProvider()` + any tools, optionally injects frameworks via `buildFrameworkContext`, returns structured output.
3. API routes under `app/api/projects/[id]/<phase>/...` — produce the artifact via `saveArtifact`, then `completePhase` (or `skipPhase` for optional).
4. UI component in `components/`, rendered by the workspace `app/project/[id]/page.tsx`.
5. Run `npx tsc --noEmit`; smoke-test the routes.

## Phases (10 stages + capture)
1. **Capture** (not a pipeline stage — the home page's New project / New agent button; voice via free Web Speech API / text / repo import) → `raw-idea`, shown as a "Show raw idea" toggle on Define the Problem / Define the Job.
2. **Define the Problem** — **Define the Job** in the agent pipeline (phase id stays `product-owner`) — an AI product owner pries at the idea with clarifying questions round after round until the real customer problem is pinned down, then synthesizes → `product-spec`. Auto-selects pm-skills playbooks per idea.
3. **Market Researcher** — *optional/skippable* (nudge to do it if monetizing). Exa forum search (demand) + market/competitor search → `market-report` with a build/refine/reject/archive verdict.
4. Pre-Marketing · 5. Product Design · 6. Development (System Design Architect; spec-driven; Claude Code executes tasks) · 7. QA (auto + **manual** + security) · 8. Deployment (Dev/UAT/Prod; AWS) · 9. Marketing & Sales · 10. Operations · 11. Iteration → loops back to Define the Problem.

## Pipeline kinds (project vs. agent)
The home page has two tabs — **Start a project** and **Create an agent** — each with a "New …" button that opens idea capture and its own list. `ProjectMeta.kind` (`project` | `agent`, missing = project) picks the phase list via `phasesFor(kind)` in `lib/pipeline.ts`; the store's gating (`completePhase`/`skipPhase`/`startNextCycle`) and every nav component read from it. The **agent pipeline** (`AGENT_PHASES`) reuses the same phase ids/modules with overrides: Define the Job (PO re-aimed at repetitive-task/agent questions via `AGENT_PO_FOCUS` in `lib/phases/product-owner.ts`; agents first answer two **basics** questions at creation — who uses it (just me / team / customers free / customers paid) and how (chat agent / background agent / both) (`lib/agent/basics.ts`, saved on the `raw-idea` as `agent_basics`) — so Define the Job is one round of ≤3 questions, Agent Design's "Who uses it" login comes from those answers via `recommendLogin`, and the agent's own local page is a chat page, a run page or both) → **Agent Design** (new id `agent-design`) → **Agent Development** (phase id `engineering`; ends with a **Safety checklist**: code checks, security checks and threat model, each red item with an AI **Fix it**; the old Security stage folded in here, `security` stays a PhaseId only for stored data) → Evaluations (the `qa` module) → Deployment → Operations, with no Iteration stage: improvements go through the Agent console in Operations. No market-research, pre-marketing or marketing stages. Agents are stamped `idea_type: "ai-agent"`.

**Agent pipeline (all 6 stages built):** `lib/agent/` holds the slot registries (`registry.ts`, `activeAdapter()`), the neutral `agent-design` shape (`design.ts`) and adapters (`adapters/langchain.ts` renders the Python agent; pytest runs through `uv`). Phases: `lib/phases/agent-design.ts`, `agent-engineering.ts`, `agent-security.ts` (safety review, run as Engineering's last step via `lib/agent/safety-review.ts`; fixes in `lib/agent/fix.ts`), `agent-evals.ts` (local eval gate; Langfuse is the tracing default); **every agent runs on the owner's computer first** (`lib/agent/local.ts`, route `deploy/local`, Deployment's "On your computer"): `templates/agent-local` (`local_app.py` + `local/index.html`) is copied into the agent folder and run as its own process on 127.0.0.1 with its own page — a collapsible **Agent Helper** (Create = the Automatic Agent Changer relayed to the pipeline via `deploy/local/helper` with a per-agent bridge key, then the agent restarts on the change; Configure = starter prompts + overview) beside **Preview · <agent name>**: a chat page (centered composer + free starter prompts from the spec's example tasks), a run page (Run now, schedule quick-starts and controls that run while the computer is awake, collapsible past runs, approvals) or both, per the basics — never inside the pipeline app; "Just me" agents stop there (Deployment completes on first start; "Use it from anywhere" opts into online), everyone else goes online after (staging on their host → production); deployment in `lib/agent/deploy.ts` + `adapters/runtime.ts` (AgentCore default, Railway) with agent-side files from `adapters/deploy-files.ts`; operations in `lib/agent/ops.ts`; cost estimate in `lib/agent/cost.ts`; skills in `lib/agent/skills.ts` (write / import + security review) and RAG index in `lib/agent/knowledge.ts`; light updates re-render from stored logic via `lib/agent/render.ts` + `agent-build/refresh`; the **Automatic Agent Changer** (side-panel chat on Agent Design; `lib/agent/builder.ts`, route `agent-builder`) edits the draft design, or on a built agent edits tool code/instructions and re-renders via `lib/agent/apply-change.ts` (shared with safety Fix it); Engineering code is written by the AI engine; **after the first build, a confirmed design change runs on its own** (`lib/agent/autoflow.ts`, started by `agent-design/approve`): rebuild → tests → safety review in the background, then — if the owner chose "always deploy automatically" and GitHub is connected — push to the agent's private repo (`lib/agent/github.ts`; before each push the **CI access slot** `lib/agent/ci-access.ts` gives GitHub keyless deploy access — on AWS an OIDC trust + a per-agent role scoped to that repo, trusting both GitHub subject formats; the generated workflow rewrites the AgentCore config's machine paths) where its agent-ci workflow re-runs tests + evals and releases staging; otherwise Deployment shows "Push & deploy now". The sidebar pulses the working stage and flags Deployment with "!" when changes wait; routes under `app/api/projects/[id]/{agent-design,agent-build,agent-cost,security,evals,deploy,ops}`; generated agents live in `~/Rapid Vibe Coding Apps/<slug>/`. **Build plan:** `release-deployment.md` — stage-by-stage tasks from the owner's research. **Hosted builds (Claude / ChatGPT):** Development has three tabs (`components/AgentDevelopment.tsx`, `lib/agent/platforms.ts`): Self-hosted agent, Claude (Anthropic Managed Agents, `lib/agent/hosted/claude.ts`) and ChatGPT (OpenAI Agents API, `lib/agent/hosted/chatgpt.ts`). The same design + code becomes a hosted agent (tools as a skill/sandbox files running `tools.py`, keys in the platform's vault, MCP sign-ins carried over); `lib/agent/hosted/sync.ts` keeps the hosted copies in step with every change; `lib/agent/hosted/evals.ts` runs Evaluations there with each case's test data in the sandbox. The tab picked in Development (`settings.agentPlatform`) scopes Evaluations, Deployment (one table row + the chat page) and Operations (`lib/agent/hosted/ops.ts`, read from the platform's session records). The sign-in chat page for hosted agents is a template app (`templates/agent-chat`, Clerk or Supabase, each user sees only their own conversations) generated into the agent's `chat/` folder and put online on Vercel (`lib/agent/chat/`). LangChain/LangSmith/LangGraph are the DEFAULT adapters, never a hard dependency: every agent tool goes behind a slot interface + registry in `lib/agent/` (framework, approval, tracing, auth, tests, evals, runtime, chat UI, web host, CI, monitoring) with neutral artifacts, so tools stay swappable. Generated agents are **Python** (LangChain-native; pytest for evals); the orchestrator stays TypeScript.

## Key decisions
- **Default stack the pipeline RECOMMENDS for apps it builds** (not the orchestrator itself): Next.js + AWS Amplify hosting + AWS Lambda + Supabase (data) + **Clerk for BOTH auth and payments** (Clerk Billing). Clerk is the standing default for the auth *and* payments slots because it covers both on one account; `reconcile()` in `lib/stack.ts` enforces that Clerk Billing can only pair with Clerk auth, and `renderAuthBilling()` in `lib/phases/engineering.ts` puts the exact wiring (env vars, `clerkMiddleware`, the `clerk_user_id` join to Supabase, `has()`/`<Protect>` feature gating) into every build briefing. Deviations warn about cost/complexity.
- **Engineering tools on the shelf for Phase 6:** OpenSpec + gsd-core (both spec-driven AI-coding execution; they overlap — pick one or compose later). Fed by `product-spec`.
- **Open-source Tool Directory (future cross-cutting feature):** pull any repo → Dockerize → host → dashboard control panel; a tool can be a standalone hosted app OR an engine wired into a phase. Build as its own feature later; keep phase engines behind interfaces.

## Conventions
- Keys/secrets: in-app paste → `data/` (gitignored). Never commit secrets.
- Every new tool/provider goes behind an interface + registry so it's swappable.
- Mobile-friendly UI (the owner drives this from a phone).
- After code changes, `npx tsc --noEmit` must pass.

## Token efficiency (agent workflow)

Two skills are vendored in `.claude/skills/` from [BuilderIO/skills](https://github.com/BuilderIO/skills) (MIT — see `.claude/skills/ATTRIBUTION.md`):

- **efficient-fable** — for token-heavy work (broad repo scans, long logs/test output, bulk docs reading, repetitive bounded edits), delegate to cheaper subagents (`model: haiku`) and keep the frontier model for decomposition, architecture, integration, and final review. **Standing authorization from the owner: spawning cheaper subagents for this purpose is pre-approved — no need to ask.** Tiny tasks and judgment-sensitive validation stay local; verify subagent findings before acting on them.
- **stay-within-limits** — before launching large parallel waves, check usage (`npx -y ccusage@latest blocks --active --json`) and pause new waves at ≥95% of the 5-hour/weekly window.
